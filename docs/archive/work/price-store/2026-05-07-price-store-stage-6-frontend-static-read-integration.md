# Price Store Stage 6 Frontend Static Read Integration

## Summary

Implement Stage 6 of the `price-store` initiative by plumbing the Stage 5
published static price artifacts into the existing card search and card-detail
UI surfaces without redesigning those screens or making any live marketplace
API calls.

This stage stays read-only from the app's perspective. It consumes
`frontend/public/data/prices/manifest.json` and the manifest-linked snapshot,
builds frontend helpers around that contract, replaces existing placeholder V0
price handling with real static data, and adds a card-detail pricing section
that can toggle exact condition-series on a 7-day history graph.

## Key Changes

- Add frontend-local typed contracts and loaders for the published price
  manifest and snapshot artifacts generated by Stage 5.
- Use a same-origin static asset flow:
  - fetch `/data/prices/manifest.json`
  - fetch the linked snapshot path from that manifest
  - cache the resolved payload in-memory for the current app session
- Normalize the published variant-row snapshot into frontend lookup helpers that
  support:
  - lookup by `tcgplayerId`
  - grouped access to all published rows for a card/version
  - grouped access by printing and condition for chart toggles
  - freshness/source metadata access from the manifest and snapshot
- Integrate price loading into the frontend app in a way that does not block
  the rest of the app from rendering when price assets are missing or stale.
- Treat Stage 6 as data plumbing into existing V0 UI locations rather than a
  visual redesign.
- Update the card search highlight price to surface the real Market Price for
  the selected card version's `Near Mint` row.
- Update the card-detail banner price surfaces below the card image to show the
  real Market Price for the selected card version's `Near Mint` row.
- Remove Market Price from the primary version/data table on the card-detail
  page so that table stays focused on row metadata rather than repeating the
  headline price.
- Add a card-detail pricing section below the `TCGPlayer` and `Card JSON` links
  that:
  - groups price-toggle buttons first by printing
  - renders one row for `Foil`
  - renders one row for non-foil only when non-foil rows exist
  - shows one toggle per available condition within that printing row
  - labels each toggle with the condition and current Market Price
  - defaults to no toggles selected
  - allows any subset of toggles to be turned on or off independently
  - shows no graph until at least one toggle is selected
  - renders a 7-day price-history graph for all selected exact series
- Keep the graph series exact to the published row contract rather than
  inventing card-level merged series:
  - each plotted line is one exact condition + printing + version row
  - alternate art or other page-level versions remain separate from the base
    version
- Define the Stage 6 default headline-price rule in frontend logic only:
  - use the selected page version
  - prefer that version's `Near Mint` Market Price
  - do not rewrite or backfill the Stage 5 stored snapshot shape
- Add graceful fallback behavior when price assets or specific series are
  unavailable:
  - no runtime crash
  - no fake placeholder price
  - no graph when nothing is selected
  - no synthetic history for sparse rows
- Cover the new frontend loaders, grouping logic, headline-price selection, and
  graph-series shaping with tests using the repo-tracked published artifacts as
  fixtures.

## Explicit Non-Goals

- No client-side calls to JustTCG or any other marketplace API.
- No visual redesign of card search or card-detail beyond the new price-history
  section and the replacement of placeholder values with real data.
- No changes to the Stage 5 publish artifact contract.
- No attempt to infer or display longer-than-available history windows such as
  24 days when the current published data is mostly 7 points deep.
- No Cloudflare scheduler, Worker, or hosted refresh work.
- No second marketplace source.
- No affiliate-link behavior.
- No requirement to add prices to Deck Explorer, Tier List, or Sealed Pools in
  this stage unless that falls out naturally from shared card UI reuse.

## Test Plan

- Run the frontend test suite and add targeted tests for:
  - published manifest loading
  - snapshot loading
  - `Near Mint` headline-price selection for search highlight and card-detail
    banners
  - condition/printing grouping for card-detail toggle rows
  - exact-series graph shaping from `priceHistory`
  - missing or malformed price-artifact handling
- Run the frontend build and verify the static asset reads are compatible with
  the bundled output.
- Manually verify the `/cards` and card-detail experience against the
  repo-tracked published price artifacts, including:
  - the search highlight price shows the selected version's `Near Mint` Market
    Price
  - the card-detail banner price shows the selected version's `Near Mint`
    Market Price
  - the primary version/data table no longer repeats Market Price
  - the pricing section appears below the `TCGPlayer` and `Card JSON` links
  - condition toggle rows are split by printing as specified
  - no graph renders when no series are selected
  - selecting one or more condition toggles renders the matching 7-day lines
  - sparse rows still render safely when selected
  - cards without matching published rows do not break the UI
- If practical, verify the app still behaves correctly when the manifest fetch
  or snapshot fetch fails.

## Assumptions

- Stage 5's published artifact contract at `frontend/public/data/prices/` is
  stable enough to consume directly in Stage 6.
- `tcgplayerId` is the right V0 join key between published price rows and the
  existing card-browsing data.
- The current published history depth is sufficient for a 7-day chart and
  should not be stretched into a longer implied window.
- A frontend-owned `Near Mint` headline-price rule is acceptable as long as
  Stage 5 keeps publishing all variant rows unchanged.
- Same-origin static asset reads are sufficient for V0 deployment on
  Cloudflare Pages.
- Completing Stage 6 will require updating the remaining Stage 7-9 draft plans
  with any new integration details or changed assumptions before those later
  stages begin.
